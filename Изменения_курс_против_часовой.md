# Изменение конвенции курса: «по часовой» → «против часовой»

Дата: 14.08.2026
Область: только код симулятора (`CorrectSimulator`). Датасет, `verify_dataset.py` и уроки курса не менялись.

## 1. Суть изменения

Во всех точках, где симулятор выражает **курс** (угол yaw), конвенция отсчёта изменена
с «по часовой стрелке» на «против часовой стрелки».

| Направление | Старая конвенция (по часовой) | Новая конвенция (против часовой) |
|---|---|---|
| Север | 0° | 0° |
| Восток | +90° | −90° |
| Юг | ±180° | ±180° |
| Запад | −90° (или +270°) | +90° |

Формально: новый курс `yaw_ccw = −yaw_cw`, где `yaw_cw` — прежний курс,
отсчитанный от севера по часовой стрелке.

Причина: такое соглашение принято заказчиком/пользователем и зафиксировано
как целевое для симулятора (угол растёт против часовой стрелки при взгляде
сверху). Это соответствует распространённой в ряде задач математической
конвенции «положительное вращение = против часовой».

## 2. Список изменений и почему каждое необходимо

### 2.1 `src/AirSimDatasetCreator/SensorRecorder.py`

**a) Docstring класса (строки 8–23)**

Было: «курс от севера по часовой стрелке» (в старой формулировке).
Стало: «курс от севера против часовой стрелки: 0=север, +90=запад».

Почему: docstring должен описывать фактическое поведение кода. Без правки
документация противоречила бы реализации и вводила бы в заблуждение.

**b) `_quat_to_euler()` (строки 54–60)**

Было:
```python
yaw_cw = np.arctan2(2 * (w * z + x * y), 1 - 2 * (y * y + z * z))
yaw = yaw_cw
```
Стало:
```python
yaw_cw = np.arctan2(2 * (w * z + x * y), 1 - 2 * (y * y + z * z))
yaw = -yaw_cw
```

Почему: формула `atan2(2(wz+xy), 1−2(y²+z²))` в NED (X=север, Y=восток, Z=вниз)
даёт угол, растущий **по часовой** стрелке при взгляде сверху. Чтобы привести
курс к целевой конвенции «против часовой», знак угла инвертируется. Инверсия
выполнена **только здесь, в единственном месте** вычисления углов Эйлера,
поэтому всё, что использует `_quat_to_euler()` (запись `angle.dat`), автоматически
переходит на новую конвенцию и знак курса не «раздваивается» по коду.

Почему инверсия именно знака, а не перестановка аргументов `atan2`:
`yaw_cw` остаётся честным промежуточным значением (физический курс от севера
по часовой), а `yaw` — это уже целевая величина в новой конвенции. Такая
запись явно показывает, что физика не менялась — менялась только система
отсчёта угла.

### 2.2 `src/AirSimDatasetCreator/TrajectoryExecuter.py`

**a) Команда `yaw_rate` (строки 153–159)**

Было: `self.client.rotateByYawRateAsync(command["yaw_rate"], command["duration"])`
Стало: `self.client.rotateByYawRateAsync(-command["yaw_rate"], command["duration"])`

Почему: значения команд в JSON-траектории теперь трактуются в новой конвенции —
**положительный `yaw_rate` = вращение против часовой стрелки**. AirSim же
интерпретирует положительный `yaw_rate` как вращение по часовой стрелке.
Поэтому перед передачей в AirSim знак инвертируется. Без инверсии положительная
команда в JSON вращала бы дрон в противоположную (неожиданную) сторону.

**b) Команда `yaw_to` (строки 161–167)**

Было: `self.client.rotateToYawAsync(command["yaw"])`
Стало: `self.client.rotateToYawAsync(-command["yaw"])`

Почему: та же логика, что и для `yaw_rate` — целевой курс в JSON теперь задаётся
в конвенции «против часовой» (положительный = запад), а AirSim ожидает угол
«по часовой». Инверсия знака приводит команду к ожиданиям AirSim.

**c) Heading в команде `velocity` (строки 83–97) — НЕ изменён**

```python
heading = math.degrees(math.atan2(command["vy"], command["vx"]))
self.client.rotateToYawAsync(heading).join()
```

Почему оставлено без изменений: этот heading вычисляется **из вектора скорости**
в мировой системе NED (`atan2(vy, vx)` даёт направление движения, отсчитанное
по часовой от севера) и передаётся в AirSim, который ожидает именно такую
конвенцию. Это **физическая ориентация корпуса** (носом по направлению полёта),
а не отчёт о курсе. Если бы знак здесь тоже инвертировали, дрон разворачивался
бы носом в противоположную сторону и летел «боком». Конвенция отчёта курса
на эту команду не влияет.

**d) Docstring класса (строки 11–22)**

Добавлено описание новой конвенции для `yaw_rate`/`yaw_to` и пояснение, что
инверсия знака выполняется перед вызовом AirSim.

Почему: документация должна объяснять, почему в коде появляется минус, чтобы
его не «исправили» обратно как ошибку.

### 2.3 `trajectories/square_1000m.json`

Было: три команды `{ "type": "yaw_rate", "yaw_rate": 45.0, "duration": 2.0 }`
Стало: `"yaw_rate": -45.0`.

Почему: траектория «квадрат» проходит **по часовой стрелке** (правые повороты
север→восток→юг→запад). В новой конвенции поворот по часовой стрелке
выражается **отрицательным** `yaw_rate` (положительный = против часовой).
Значение −45°/с × 2 с = −90° (против часовой) → после инверсии знака в коде
в AirSim уходит +90° (по часовой), и физический полёт по квадрату остаётся
точно таким же, как раньше. Без этой правки дрон начал бы поворачивать в
противоположную сторону на каждом углу, и датасет перестал бы соответствовать
описанию «полёт по квадрату».

Аналогично, команда `{ "type": "yaw_to", "yaw": 0.0 }` не требует изменений:
0° одинаково в обеих конвенциях.

## 3. Чего не менялось и почему

- **Датасет `correct_ver_mav_square_1000m`** — не перегенерирован: по решению
  пользователя работаем только с кодом симулятора. Существующие файлы остаются
  в старой конвенции (курс по часовой).
- **`verify_dataset.py`** — не менялся: он анализирует существующий датасет и
  оперирует в старой конвенции. Для новых (перегенерированных) данных этот
  инструмент потребует согласования (знак |yaw−курс| станет ~2·|yaw|), но это
  выходит за рамки текущей задачи.
- **Уроки Python-курса** — не менялись, так как опираются на существующий датасет.

## 4. Ожидаемый эффект

- `angle.dat` (yaw) новых полётов: 0°=север, +90°=запад, ±180°=юг, −90°=восток.
- Команды `yaw_rate`/`yaw_to` в JSON: положительное значение = против часовой.
- Физическое поведение полёта по квадрату (`square_1000m.json`) — без изменений.
- Углы крена (roll) и тангажа (pitch) — без изменений: они не зависят от
  конвенции отсчёта курса.
